# ManyManager UI reference

Current Android behavior and maintenance rules: [ManyManager documentation](../docs/README.md); [release guide](../docs/release.md).

This is a lightweight design reference. Keep its appearance and essential UI interactions aligned with Android so future design experiments start from an accurate visual baseline. Simplifying duplicated logic, implementation and testing burden is a separate task; preserve visual synchronization and existing tests meanwhile.

An interactive HTML/CSS/JavaScript companion to the Android XML interface. Both implementations share navigation, category/source interactions, expense creation, read-only details, in-place full editing, confirmed deletion, and filtered expense lists. Android uses persistent Room data; the browser uses an isolated in-memory preview.

## Run

From the repository root:

```sh
python -m http.server 8000 --directory ui-reference
```

Open http://localhost:8000/ . The entry point is `index.html`. ES modules and fetched locale JSON require an HTTP server.

## Approved unified summary cards

Android and the preview implement the approved unified category/source cards: a keyboard-operable header and expense rows inside one rounded surface, with subtle dividers. Rows show a prominent amount, contextual date/classification, and a two-line note preview. All Expenses uses the same hierarchy without grouping. Multiple groups can stay expanded. The details/edit/delete dialog is unchanged. Android matches this hierarchy and spacing with native Views; exact font metrics and pixel parity are not promised. This is post-0.1.0 development and does not change the previously signed APK.

For an optional populated visual example, open http://localhost:8000/tests/summary-cards.html . It uses an isolated iframe with an explicitly imported fixture; the default app still starts empty, and all browser data remains in memory. Use the app’s settings to try Hebrew/Russian/English and light/dark. Run `/tests/summary-cards-checks.html` for focused checks alongside the existing expense checks.

Browser verification of the approved design: Edge headless passed 37 focused card/layout/interaction checks with normal motion and again with reduced motion, plus the existing expense-details (65), stage8 (32) and stage9 (35) checks. These cover 320px layouts in he/en/ru × light/dark, duplicate/null groups, note truncation, direct details, scroll/expansion retention and saved mutations. ## Screens and interactions

The side menu opens Home, Expense Summary, Budget Management, Expense Categories, and Settings. Settings contains only Language and Appearance. Expense Categories retains its existing list, Back action to the previous page, and Add Category dialog.

Budget Management keeps the existing month arrows and total card. It lists the same source identities offered in the expense sheet. Add Source accepts a name and an initial allocation for the selected budget period, captured when the form opens. Tapping a source opens its editor with a source name, current allocation, positive adjustment magnitude, +/− selector, signed resulting allocation preview, Cancel, and Update budget. Empty adjustment means zero change. A confirmed adjustment changes the selected period’s allocation once and never creates an expense. The existing allocation rule rejects a negative allocated budget; its signed preview remains visible. Remaining balance may be negative.

The Add Expense sheet offers “＋ New category” after its category choices, including when the list is empty. It reuses the Add Category form. Category choices and draft selection use stable category IDs. Confirming selects the new category by ID; Cancel and Back/Escape return to the unchanged expense draft. Amount, source, date, note, and category selection remain in the draft during this transition. Android keeps the expense sheet beneath the category dialog; the web reference temporarily renders the category dialog and restores the same draft.

The initial state is Hebrew, RTL, light theme, home screen, current month, and no categories, sources, budgets, or expenses. Android categories, budget sources, period allocations, and expenses persist in Room SQLite across process restarts. Browser categories, sources, allocations, expenses, appearance, and drafts live only in memory and reset on reload. No sample records or browser storage service are present.

## Expenses

Save accepts an exact positive amount in minor units, an optional category (Uncategorized), a required persistent source, a civil date, and an optional note. Zero and negative amounts/refunds are unsupported. Zero-allocation sources and negative remaining balances are allowed. Android uses a native date picker and LocalDate; the preview uses a date input and YYYY-MM-DD civil strings through the central period helper. The expense date determines its accounting period.

All expenses shows the active period, newest date first with an ID tie-breaker. Tap a row to open read-only details, with a note only when present. Edit replaces the values with controls in that same view: amount, date, category (including none), source, and note. Save updates the same ID and returns to saved details without closing. Cancel or Back in edit mode discards the draft; Back from details returns to the list. Delete appears only in edit mode and requires confirmation; cancelling confirmation preserves every draft field. Home totals, counts and remaining balances derive from the same snapshot. Allocations stay unchanged. Category and source tabs now show the active period’s spending and expense count, ordered by spending descending then stable ID (null category first on a tie). Duplicate names remain separate rows. Uncategorized is a translated null group, not a category record. Only groups with expenses appear, including zero-allocation sources. Tapping a group header toggles expense rows inside that same rounded card in Summary, even with one row. Subtle dividers separate the header and rows; there are no nested rounded row cards. Category rows show date/source, source rows show date/category, and All Expenses shows all classifications. Amounts are prominent and optional note previews are limited to two lines, with full notes in details. A chevron and aria-expanded expose its state. Groups use stable IDs, including null category, and the containing Summary snapshot period. Long lists use the page’s normal scroll without a nested scrolling viewport. Details open as a dimmed overlay above Summary; closing keeps the tab, expansions and scroll position, naturally clamped if content shrinks. An emptied group disappears normally. There is no separate group page, list dialog or sheet. Details remain open after Save even if the record leaves that filter. Saved observations never overwrite a dirty draft. Save/Cancel occupy the start side and destructive Delete the end side (Hebrew right/left; English/Russian left/right).

Android ViewModel owns editable/submitting/success/failure states for both expense forms. Pending writes cannot be cancelled or submitted twice; creation/deletion close only after commit, while editing returns to read-only details in the same window. Known failures preserve input for explicit retry. Normal Activity recreation and configuration rebuild restore the form without replay. A restored Bundle marked submitting locks the form: close and inspect All expenses before deliberately starting another operation. A Bundle is not durable draft storage or an exactly-once guarantee after arbitrary process death, including a stale Bundle saved before submission.

These details/edit/delete/group flows are post-0.1.0 development work, not features of the previously signed private APK. Add Expense retains its original interface. Run `/tests/expense-details.html` for focused model, real app events, and 320px locale/theme action-placement checks. See [historical verification and limits](../docs/archive/expense-details.md); the stage results below describe earlier deliveries.

## Summary state and consistency

Android SummaryBreakdownUi renders both panels from the same activeBudget snapshot as Home and All expenses. Category names and grouped amounts come from that snapshot. Independent category/source observations still serve choices and management; their loading or failure cannot replace a valid financial panel. Financial loading, successful empty, and failure with retry are distinct.

SourceBudget already contains spending/count/remaining. BudgetCalculations orders category groups, and BudgetSnapshot exposes ordered sourceBreakdown without regrouping expenses. Browser snapshotFor prepares the same rows in the isolated preview model; screens only format and bind them. No percentages or charts were added. Home and all summary tabs use one callback/revision. Budget Management and choice streams update independently and converge on committed facts; no claim of simultaneous frames across streams is made.

## Budget periods and verification

Periods run from the 10th through the 9th by default. Android uses the saved calculator setting through BudgetPeriodCalculator; the browser has one civil-date helper in js/budget-period.js. A deliberate menu entry into Budget Management selects the active period and its arrows select adjacent periods. Back restores the historical selection; rebuilding Android views or recreating the Activity keeps it. Forms retain their captured period. Home follows the active period independently of management selection, including before the 10th. The preview refreshes on return/focus and checks visible civil-date changes once a minute, while captured form periods and historical selections remain unchanged. A new period has zero allocation and retains all sources, with no copying or carry-over. Summary arrows remain disabled.

Android observes sources independently from financial snapshots and renders loading, empty, populated, and error states with explicit retry. Source form submission is owned by the ViewModel; pending forms cannot submit twice or be cancelled. Known failed writes retain the input. On Android, a Bundle restored from an interrupted source write has an unknown outcome: that form is locked against resubmission. Close and check saved data returns to its captured period; a new operation must be started deliberately. Bundle recovery is not a durable draft or an exactly-once guarantee after arbitrary process termination. The browser does not emulate Android process lifecycle. Resume and date/time/zone broadcasts refresh active data without replacing historical selections. The preview is synchronous, resets on reload, and has no simulated production storage or automatic retries. Its money range is JavaScript safe integers in minor units, narrower than Android Long.

Android verification passed 31 JVM checks, 36 repository/controller checks, 12 database checks, and 9 real Activity/dialog checks after fixing an existing rollover test wait. The full language/theme visual matrix and API 30 were not reverified for the new expense dialogs. Open /tests/stage6.html to run 27 focused browser assertions (stages 6–7). They cover period boundaries, stable source IDs, atomic validation, zero allocations, draft preservation and category return/cancel. The checks include year-crossing labels with both years, accessible localized date ranges, and confirmation/cancellation after period rollover. They passed in Chrome on Android 17. They do not prove pixel parity or Android lifecycle behavior. Android verification and remaining lifecycle checks are recorded in [the historical report](../docs/archive/persistent-data-plan.md).

## Viewport and fidelity

The layout is capped at 440 CSS px on desktop and fills a narrow phone browser. The Android source uses a 440dp cap with system insets. CSS px are not physical screenshot pixels. Browser font metrics, native EditText behavior, IME, system bars, ripple effects, and native AlertDialog appearance can differ. No fake system bars are drawn.

This document describes the intended behavior. Check the current task report for verification actually performed. Browser and Android rendering can differ; pixel-level visual equivalence has not been established.
